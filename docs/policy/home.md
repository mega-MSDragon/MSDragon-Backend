# 홈 화면 정책

확정된 홈 디자인에 맞춰 사용자별 안내 상태와 여행 카드, 월별 추천 도시, 축제 데이터를 구성하는 정책입니다.

## 권한과 노출 상태

- 가족 여행 생성 권한은 자녀에게만 있습니다.
- 홈 응답에 별도 `canCreateTrip`을 두지 않고 클라이언트가 `userRole=child`인지 확인합니다.
- 자녀 홈은 여행이 없을 때 `새 여행 추가하기`를 노출합니다.
- 부모 홈은 여행이 없어도 여행 생성 버튼을 노출하지 않습니다.
- 자녀에게는 연결된 부모 전체와 각 부모의 `profileCompleted`를 반환합니다.
- 부모에게는 가족 매칭 여부와 관계없이 본인의 `profileCompleted`를 반환합니다.
- 클라이언트는 부모별 `profileCompleted=false`를 기준으로 프로필 작성 또는 요청 UI를 구성합니다. 별도 안내 type은 사용하지 않습니다.
- `부모님께 부탁드리기` 실제 푸시는 기기 토큰과 알림 정책이 확정될 때까지 보류합니다.
- `나중에 하기`는 앱 로컬 상태로 처리하며 DB에 저장하지 않습니다.

## 홈 여행 목록

- 홈에는 `in_progress`, `planning`, `ready` 여행을 노출합니다.
- `stopped`, `archived` 여행은 홈에서 제외합니다.
- **`completed` 여행은 역할에 따라 다르게 노출합니다.** 홈은 지금 할 일을 보는 화면이므로 끝난 여행을 계속 쌓아두지 않습니다.

| 역할 | `completed` 여행 노출 |
|------|----------------------|
| 자녀 | **노출하지 않습니다.** 기록 탭(`GET /api/v1/records`)에서 확인합니다 |
| 부모 | **아직 평가하지 않은 여행만** 노출합니다. 평가를 제출하면 홈에서 사라집니다 |

- 부모 노출 조건은 **해당 여행의 참여자이고 본인 피드백이 없을 때**입니다. 참여자가 아닌 부모는 평가할 수 없으므로 노출하지 않습니다. 노출하면 사라지지 않는 카드가 남습니다.
- 부모에게 남은 완료 여행 카드는 평가 유도 용도입니다. `ratings[]`에는 이미 제출한 다른 부모의 별점이 담기므로, 아직 평가하지 않은 부모도 배우자의 별점을 볼 수 있습니다.
- `in_progress` 여행을 먼저 표시하고, 이후 완료·예정 여행을 시작일과 ID 오름차순으로 표시합니다.
- 서울 날짜 기준으로 조회 시점에 여행 상태를 동기화합니다.
- 미래 여행의 `dDay`는 `시작일 - 오늘`의 날짜 차이입니다. 진행 중인 여행은 `null`입니다.
- 당일치기 여행은 `dayTrip=true`로 반환합니다. 클라이언트는 `startDate`만 한 번 표시하고, 그 외 여행은 시작일과 종료일을 함께 표시합니다.
- 각 여행의 `ratings`에는 피드백을 제출한 부모의 사용자 ID, 이름, 관계명, 별점을 부모 ID 순으로 반환합니다. 부모 두 명의 점수를 평균으로 합치지 않습니다.
- 아직 부모 피드백이 없으면 `ratings=[]`이며, 클라이언트는 완료 카드의 미작성 상태를 표시할 수 있습니다.

## 여행 카드 대표 테마

- 여행 생성 당시 `recommendationSnapshot.parents[].travelThemes`를 사용합니다.
- 참여 부모 전체에서 선택 빈도가 가장 높은 테마 하나를 `primaryTheme`으로 반환합니다.
- 동률이면 아래 고정 우선순위에서 앞선 테마를 사용합니다.

1. `nature_scenery`
2. `history_culture`
3. `shopping`
4. `activity`
5. `culture_life`
6. `landmark`
7. `experience`

추천 스냅샷이 없는 기존 여행은 `primaryTheme=null`입니다.

## 여행 강도

부모가 두 명이면 가장 천천히 걷는 부모를 기준으로 계산합니다.

| walkingPace | intensity | 화면 표시 |
|-------------|-----------|-----------|
| `slow` | `low` | 여행 강도 낮음 |
| `normal` | `normal` | 여행 강도 보통 |
| `fast` | `high` | 여행 강도 높음 |

추천 스냅샷이 없는 기존 여행은 `intensity=null`입니다.

대표 이미지는 **서버에 넣어둔 도시 이미지**를 사용합니다. `src/main/resources/static/images/destinations/{destinationCode}.png` 12장을 정적 리소스로 제공하고, `imageUrl`에 `{APP_BASE_URL}/images/destinations/{destinationCode}.png`를 담아 반환합니다.

- 도시는 `TripDestinationCode` 12개로 고정되어 있어 외부 조회 없이 파일로 관리합니다. 홈 첫 화면에서 TourAPI 왕복 5회가 사라져 로딩이 빨라지고 외부 장애 영향도 받지 않습니다.
- 이미지는 인증 없이 URL로 제공됩니다. 정적 리소스 경로는 인증 인터셉터(`/api/v1/**`) 대상이 아닙니다.
- **파일이 없는 도시는 TourAPI 조회로 넘어갑니다.** 12장을 한 번에 채우지 않아도 기존 동작이 유지되므로 이미지를 점진적으로 추가할 수 있습니다.
- 이미지를 교체하려면 같은 파일명으로 바꾸고 서버를 재배포합니다. 파일이 jar에 포함되므로 배포가 필요합니다.
- `APP_BASE_URL`을 운영 도메인으로 설정해야 합니다. 응답이 일 단위로 캐시되므로 요청 호스트를 추론하지 않고 설정값을 사용합니다.

TourAPI 폴백 경로는 국문 관광정보 서비스 `KorService2/areaBasedList2`를 이미지 우선 정렬 `arrange=Q`로 조회합니다.

## 추천 축제

국문 관광정보 서비스의 아래 API를 사용합니다.

| 목적 | Operation | URL |
|------|-----------|-----|
| 축제 목록 | `searchFestival2` | `https://apis.data.go.kr/B551011/KorService2/searchFestival2` |
| 축제 소개 | `detailCommon2` | `https://apis.data.go.kr/B551011/KorService2/detailCommon2` |

- 서울 날짜 기준 오늘부터 30일 뒤까지 조회합니다.
- 진행 중이거나 조회 기간 안에 시작하는 결과만 사용합니다.
- 대표 이미지가 있는 결과를 우선하는 `arrange=Q`를 사용하고 최대 10개를 반환합니다.
- 목록 결과마다 `detailCommon2`의 `overview`를 HTML 제거 후 최대 180자로 요약합니다.
- 태그는 주소에서 추출한 지역명과 `축제`를 반환합니다.

## 캐시와 장애 처리

- 추천 도시 이미지와 축제는 모든 사용자에게 같은 데이터이므로 서로 독립된 애플리케이션 메모리에 서울 날짜 단위로 캐시합니다.
- 서울 날짜가 바뀐 뒤 해당 섹션의 첫 조회 또는 서버 재시작 뒤 첫 조회에서 관련 TourAPI만 다시 호출합니다.
- 새 날짜의 조회가 실패하면 직전 캐시를 사용합니다.
- 직전 캐시도 없으면 도시 이미지는 `null`, 축제는 빈 목록을 반환합니다.
- TourAPI 장애나 서비스키 누락은 해당 추천 또는 축제 API의 축소 응답으로 처리하며 나의 여행 API에는 영향을 주지 않습니다.

## DB 정책

- 홈 전용 테이블은 추가하지 않습니다.
- 여행 카드 값은 `trips.recommendation_snapshot`에서 계산합니다.
- 완료 카드 별점은 `trip_feedbacks`에서 조회하며 홈 전용으로 복제하지 않습니다.
- 추천 도시 정책은 서버 코드로 관리합니다.
- 축제와 도시 이미지는 일 단위 메모리 캐시만 사용합니다.
- 운영 도구에서 추천 콘텐츠를 편집해야 하는 요구가 생기면 그때 별도 마스터 테이블을 도입합니다.

## 동적 섹션

홈 축제 영역부터 아래까지는 **섹션 목록**으로 제공합니다. 섹션을 늘리거나 순서를 바꿀 때 앱을 고치지 않는 것이 목적입니다.

### 계약

- 응답의 배열 순서가 **화면 노출 순서**이며 서버가 결정합니다. 클라이언트는 재정렬하지 않습니다.
- **모든 섹션은 같은 카드로 그려집니다.** 섹션이 늘어나도 내용만 달라집니다. 그래서 섹션 종류를 응답에 내리지 않고, 클라이언트에 섹션별 분기도 두지 않습니다.
- 그 결과 **섹션 추가·삭제·재정렬·제목 변경·항목 내용 변경이 모두 서버에서 끝납니다.** 앱 수정이나 스토어 심사가 필요하지 않습니다.
- 섹션마다 다른 부가 정보는 `caption`에 **서버가 문장으로 만들어** 담습니다. 축제는 기간(`2026.08.01 - 08.31`), 관광지는 지역입니다. 축제 날짜만 별도 필드로 두면 카드가 섹션 종류를 알아야 하므로 필드를 나누지 않습니다.
- 항목이 `contentTypeId`를 들고 있어 클라이언트가 섹션 종류를 몰라도 상세로 이동할 수 있습니다.
- 외부 API 장애 시 **섹션은 남기고 `items`만 빈 배열**로 축소합니다. 섹션을 아예 빼면 화면 구성이 날짜마다 달라져 예측하기 어렵습니다.

### 구성과 순서

`HomeSectionPolicy.sections`의 순서가 노출 순서입니다. **순서를 바꾸려면 이 목록의 순서를 바꿉니다.**

| 순서 | `key` | 내용 |
|------|-------|------|
| 1 | `festivals` | 오늘부터 30일 이내 축제 최대 10개 |
| 2 | `monthly_attractions` | 이번 달 추천 도시 5곳의 관광지, 도시당 2개 |

- `HomeSectionSource`는 항목을 어디서 채우는지 고르는 **서버 내부 값**이며 응답에 나가지 않습니다. 같은 출처로 섹션을 여러 개 둘 수 있습니다.
- 섹션 구성은 **코드로 고정**합니다. 월별 추천 도시(`HomeRecommendationPolicy`)와 같은 방식입니다. 어드민 도구가 없는 상태에서 DB로 관리하면 SQL을 직접 실행해야 해 실익이 없습니다.
- 운영 중 비개발자가 섹션을 바꿔야 하는 시점에 **응답 계약을 유지한 채 데이터 출처만 DB로 옮깁니다.** 계약이 먼저 고정되어 있어 그때도 클라이언트를 고치지 않습니다.

### 관광지 섹션

- 이번 달 추천 도시(`HomeRecommendationPolicy`)를 기준으로 조회해 월별 추천 도시 섹션과 내용이 이어지도록 합니다.
- TourAPI `areaBasedList2`에 `contentTypeId=12`(관광지)와 이미지 우선 정렬 `arrange=Q`를 사용합니다. 숙박·행사는 섞지 않습니다.
- **이미지가 없는 관광지는 제외합니다.** 카드가 비어 보이는 것을 막기 위함이며, 그래서 도시당 요청 수를 목표 개수의 3배로 두고 이미지가 있는 항목만 취합니다.
- `contentId` 기준으로 중복을 제거하고 도시 순서를 유지합니다.
- **한 도시 조회가 실패해도 나머지 도시 결과를 반환합니다.** 도시 하나 때문에 섹션 전체가 비지 않도록 도시 단위로 실패를 격리합니다.
- 부제는 이번 달 추천 도시 이름을 `·`로 이어 붙입니다.

### 캐시

- 섹션 응답은 축제·추천 도시와 마찬가지로 **서울 날짜 단위 메모리 캐시**입니다.
- 축제 섹션은 `/festivals`와 **같은 캐시를 재사용**해 TourAPI를 두 번 호출하지 않습니다.

### `/festivals` 처리

`GET /api/v1/home/festivals`는 `festivals` 섹션으로 대체되었으나 **제거하지 않습니다.** 심사 중이거나 이미 배포된 앱 버전이 호출하고 있어 제거하면 그 버전이 깨집니다. 해당 버전이 사용되지 않게 되면 제거하고, 그때까지는 Swagger와 문서에 deprecated로 표기합니다.

### 섹션 항목 상세

섹션 항목을 탭하면 `GET /api/v1/places/{contentId}?contentTypeId={item.contentTypeId}`로 이동합니다.

- 여행 코스의 방문지 상세와 **같은 응답 형태**를 사용해 클라이언트가 상세 화면을 재사용합니다. 여행 권한 검사만 없습니다.
- **축제 상세 API를 따로 두지 않습니다.** 축제도 TourAPI 콘텐츠(`contentTypeId=15`)라 같은 엔드포인트로 조회합니다.
- 원본 API가 값을 채우지 않는 필드가 많으므로 상세 화면은 고정 레이아웃이 아닌 **가변 섹션 구조**로 설계합니다.
- 무장애 원문의 빈 값은 '이용 불가'가 아니라 '정보 미제공'입니다. 서버는 빈 값을 그대로 전달합니다.

`2026-09-02` 공공 API 검토(`parent-friendly-places-festival-api-review`)의 권장 계약과 같은 방향이며, 축제 상세만 별도 엔드포인트로 두지 않고 통합했습니다.
